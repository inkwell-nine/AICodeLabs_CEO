    What this is

    Eleven hands-on labs that take you inside the modern AI stack: open-source and frontier models, routing, costs, harnesses, tools and MCP, retrieval, agents, and evals. You won’t read about these things. You’ll build small versions of each with an AI coding agent (Claude Code) doing the typing while you make the decisions.

    The goal isn’t to turn you into a developer. It’s to give you first-hand intuition for how these systems actually work, so you can make sharper calls about your product’s AI roadmap, your AI unit economics, build vs. buy, and how your teams use agents, and ask your CTO and your vendors better questions.

    Everything here is optional and self-paced. Each lab takes 60–90 minutes. Most cost a few dollars in API credits. Lab 10 (multi-agent pipeline) is the outlier at roughly $10–50. Budget about $25–75 if you do all eleven.

    Before you start: guardrails

    These labs have you install command-line tools, create API keys, and let an AI agent run commands on your machine without asking you before each one. That’s the point, and it’s safe when the setup is right. Five rules:

    The five rules
    1. Use a sandbox machine. A personal laptop or a dedicated spare machine is ideal. If you want to use your company laptop, check with your IT or security lead first.
    2. No company or customer data. Ever. Every lab works on synthetic or public data, and most have Claude generate the data for you. If you’re tempted to try a lab on real material, anonymize it heavily, or better, don’t.
    3. Personal accounts, small limits. Sign up for API platforms with a personal email. Load prepaid credit ($5–20 at a time) instead of attaching open-ended billing, and set spend caps wherever the platform offers them.
    4. Give your CTO or security lead a heads-up. Installing developer tools and running an AI agent that executes commands can trip endpoint-security alerts. A two-line note avoids a surprise. They may also want to do a lab with you, and the conversation afterward is half the value.
    5. Clean up when you’re done. Revoke the API keys you created and delete the lab folders. Keys belong in a .env file inside the lab folder. Never paste them into a chat, and never commit them to a repository.

    • A Mac is easiest. The labs are written with macOS in mind. Claude Code also runs natively on Windows (installing Git for Windows is recommended) or inside WSL. Where a lab shows a Mac-specific step, ask Claude to translate it for your machine. It handles this well.

    Install Claude Code

    Claude Code is Anthropic’s agentic coding tool. It reads files, runs commands, and writes code in a folder you point it at, while you steer in plain English. It comes in a few forms: a terminal app, a tab in the Claude desktop app, IDE extensions, and a web version. These labs use the terminal app, because watching the agent work command by command is half the lesson. Product page: claude.com/product/claude-code.

    1. Open a terminal. On a Mac, press Cmd + Space, type Terminal, and press Enter. Never used one? Anthropic’s terminal guide walks through the basics in a few minutes.
    2. Run the installer for your system. This is Anthropic’s official native installer, and it keeps itself up to date.

      macOS, Linux, or WSL:

      curl -fsSL https://claude.ai/install.sh | bash

      Windows (PowerShell):

      irm https://claude.ai/install.ps1 | iex

## How to talk to me

- **Calibrate to the "How technical I am" line above.** Don't over-explain things I already know or skip things I don't. If you're unsure, ask once.
- **Use my analogies when they hold up.** When you introduce a new concept, an analogy from the list above can help, but a stretched analogy is worse than none. If there isn't a clean one, explain it in plain English.
- **Explain AI concepts on their own terms.** Tokens, embeddings, RAG, harnesses, agents, and evals are what these labs are designed to teach. I want to learn what they actually are.
- **Explain why before what.** Before you install something, write a script, or take an action, give me one sentence on *why* it's the right move. Then do it.
- **Plain English by default.** If you have to use a term I might not know, define it in the same sentence ("a tokenizer, the thing that decides how a model counts and charges for text").
- **Narrate when you act.** When you run a command, write a file, or call a tool, tell me in one sentence what you just did.
- **Don't tell me things are "simple," "easy," or "trivial."** Let me decide.
- **Push back when I'm asking the wrong question.** If I ask for X but the right move is Y, say so. I'd rather you correct me than humor me.
- **Connect it to running a company when it's useful.** If a concept has a clear implication for a software business (product architecture, inference cost, security, how engineering teams work), name it in a sentence or two. Don't lecture.

## What good looks like

**Less good:** *"I'll just pip install fireworks-ai and add it to your `.env`."*

**Better:** *"I'm about to install the Fireworks Python library, a small package that lets our script talk to Fireworks' servers. Then I'll save your API key in a `.env` file, a separate file that holds secrets so they never appear in the code itself. Going ahead."*

**Less good:** *"That's a tokenization issue."*

**Better:** *"That's a tokenization issue. The model splits your text into chunks before it reads it, and different models count chunks differently. The same sentence might be 30 chunks to one model and 22 to another, which changes the price. Want me to show you the count?"*

## Keep a record

- **Save what you run.** When you run a script or call an API, save the full output to a file in this folder (an `outputs/` folder is fine) and tell me the file name.
- **Check the record before re-running.** If I ask a follow-up question about something that already ran, read the saved output first. Only re-run it if the answer isn't there, and tell me before you do.

## A reminder for both of us

This is a learning exercise, not a production project. Pick the path that teaches me the most about the *shape* of the thing, not the path that produces the cleanest artifact. If two approaches both work but one is more revealing, use the more revealing one.

    Why --permission-mode auto --effort max

    You’ll see this command in every codelab’s “Before you start” section. The reasoning is the same every time, so we’ve put it here once.

    Why these flags

    --permission-mode auto lets Claude work without asking you to approve every command, file write, or install, which is the let-Claude-drive feeling these codelabs depend on. In auto mode, a second safety model reviews each action before it runs. Routine work in your folder goes through, and risky moves get stopped and handed back to you: piping a script from the internet into your shell, sending data to an unknown endpoint, touching things outside the task. When it stops and asks, read the request and decide. That pause is the guardrail working. In recent versions auto mode is already the default, so the flag just makes it explicit.

    Don’t reach for --dangerously-skip-permissions. You’ll see it in older tutorials. It turns every check off, and Anthropic’s docs reserve it for isolated containers and VMs. If auto mode isn’t available on your account, use --permission-mode acceptEdits instead and approve commands as they come up. You can also switch modes mid-session with Shift + Tab. Auto mode is a strong second line of defense, not a substitute for the guardrails above: a sandbox machine, no company data, small credit limits.

    --effort max tells Claude to think as hard as it can on every step. During a learning exercise you want the strongest version of the model, not the cost-saving one. It does use your plan’s limits faster. If you hit a limit, drop to --effort high.

    The mindset, in three sentences

    • Tool-first, not hand-first. When a platform has a CLI, install it and hand it to Claude. When it has only an API, generate a key and let Claude write the calls. You almost never click through a UI.
    • Stuck is the lesson. When something breaks or doesn’t make sense, paste it back into Claude and ask. The way out of friction is almost always the agent, not a search engine.
    • You provide judgment; Claude provides typing. Decisions, observations, taste, and ownership are yours. Recording, scripting, formatting, timing — those go to Claude.

    Tips that will save you time

    These come from people who ran through the labs before you. Skim them now, then come back when you hit a snag.

    Setup

    • command not found after installing Claude Code usually means it isn’t on your PATH. Open a new terminal window first. If that doesn’t fix it, run claude doctor or see the install troubleshooting link above.
    • Homebrew prints PATH instructions at the end of its install. Run them. If you skip them, everything you install with Homebrew afterward silently won’t be found.
    • Check your Python before Lab 6. macOS often ships an older Python 3. The MCP SDK needs 3.10 or newer, and the failure looks like a cryptic install error. Run python3 --version. If it’s below 3.10, ask Claude to upgrade it or take the Node.js path.
    • Your first charge on a developer platform may trigger a card fraud alert. Keep your phone nearby to approve it.
    • If your Claude plan doesn’t give you Anthropic Console access (common on company plans), you can’t create an Anthropic API key there. Use OpenRouter, or create a personal Console account for the labs that need a direct key.

    Running the labs

    • Read the full opening prompt before pasting it. The summary at the top of each lab is a teaser, not the instruction.
    • Save results as you go. The Keep a record section of your CLAUDE.md already tells Claude to save every output to a file in the lab folder. If you notice it isn’t, tell Claude: “From here on, save all outputs and results to a markdown file in this folder.” That way you never pay twice to see a result you already generated.
    • Auto mode will occasionally stop and ask. Some installers, like Homebrew’s, work by downloading a script and running it. Auto mode blocks that pattern by default and hands it to you. If it’s the official installer for a tool the lab asked for, approve it. If you’re not sure what you’re approving, ask Claude to explain first.
    • /rewind is your undo button. Press Esc twice (or type /rewind) to roll the conversation and Claude’s file edits back to an earlier point. It can’t undo things that happened outside your folder: installs, API calls, or anything pushed to the internet.
    • Closed the terminal by accident? Run claude --continue in the same folder to pick up the conversation where you left off.
    • Watch what you’re spending. /usage shows the session’s cost and, on a subscription, how much of your plan’s limit you’ve used. (Older tutorials call it /cost, which still works.)
    • If Claude gets ahead of you, say: “Please pause. Describe exactly what you’ve done so far and what state the project is in.” Then decide whether to continue or reset.
    • If you’re not getting the point of a lab, say so and go off script. The labs are scaffolding, not a test.
    • Know which waits are normal. Lab 1 downloads a 3–7 GB model. Lab 3’s benchmark runs for several minutes and costs real money, so don’t interrupt it or you’ll pay to re-run it. Labs 9 and 10 are designed to run while you’re away from the keyboard. A quiet terminal is almost never a stuck one. If you’re unsure, paste the screen into Claude and ask whether it’s expected.
    • Lab 4 compares models inside Cursor. Cursor’s free plan may limit which models you can pick. A Pro plan or the free OpenCode alternative gets around this.
    • Check your credit balance before Lab 10. It’s the most expensive lab by a wide margin.

    Things that surprise people

    • Models don’t do arithmetic. They call tools. When a calculation comes back wrong, the problem is usually the tool call (wrong inputs, wrong formula), not the model’s intelligence. If two models give different answers on a calculation, check whether both actually called the tool.
    • Per-token price isn’t per-task price. A model at a fraction of the frontier per-token rate can cost the same per task if it thrashes. One participant saw 97 tool calls on a run a frontier model finished in 3. Watch the call count, not just the rate card.
    • Bigger isn’t always better. A smaller model that calls the right tool correctly beats a bigger one that tries to reason its way around it.
    • Model names and prices change monthly. Where a lab names a specific model, treat it as an example. Every lab has Claude look up the current catalog, so trust that over this page.

    Contents

    The eleven codelabs are sequenced — earlier ones set up tools and intuitions that later ones rely on. Reading the arc once before you start makes the dependencies visible and helps you pick a starting point that fits where you are.

    Chapter 1

    Foundation

    Chapter 1 is the foundation. The goal is to come out knowing how to download an open-source model, how to get it running on your laptop, and which model sizes fit which kinds of hardware. Everything downstream assumes you’ve handled at least one model end-to-end.

    01Open-source models & local hosting

    Pull a small open-source model from Hugging Face onto your laptop and get it answering prompts. The exercise is mostly about two practical things: how to download a model via the CLI rather than clicking around the website, and which model sizes are realistic for which kinds of machines — the memory math that decides whether a ~4B model is your ceiling or whether you can run a ~9B comfortably. A comparison against Kimi K3 on a Fireworks endpoint at the end gives you a feel for what local can and can’t do.

    Why it matters for a CEO If your customers are regulated or security-conscious, someone will ask whether your AI features can run in their VPC, on-prem, or without data leaving the building. Local and self-hosted open models are a real answer, but you give up capability in exchange for control. Knowing roughly which model sizes fit on which hardware lets you weigh that trade-off honestly, and lets you check vendor claims like “edge-deployable” or “runs on your hardware.”

    Chapter 2

    The access layer

    Most production AI systems aren’t pointed at one provider. They go through an intermediary that fans out to many. Once you’ve felt the model-versus-hosting distinction, the next move is reaching every model with a single key.

    02Model routing

    Set up OpenRouter — one API key, every major model — and build a router that sends each prompt to the cheapest model that meets a quality bar. We do this codelab early because the next two depend on having OpenRouter set up.

    Why it matters for a CEO Routing is how serious AI products keep inference costs under control: cheap models handle the easy calls and frontier models handle only the hard ones. It also means you aren’t tied to one provider. If your product is hard-wired to a single model, ask your team how long it would take to switch providers if pricing or quality moved. The right answer is days, not quarters.

    03Performance & cost benchmark

    Run the same ten prompts through ten OpenRouter models. Measure cost per token, latency, tokenizer differences, and spot-check quality. Now that you can reach every model, the next question is which one to use for which kind of work.

    Why it matters for a CEO The same prompt can cost 100× more on one model than another. Once you’ve seen that spread yourself, you have a baseline for estimating AI cost per customer, pricing an AI feature without eroding gross margin, and checking the inference-cost numbers your team or a vendor gives you.

    04Harness–model coupling

    Swap the model behind Cursor on the same coding task, then run that task through a second harness (OpenCode) with yet another model. Watch how the same harness behaves differently with different models behind it. The point is that the harness and the model are two different choices.

    Why it matters for a CEO When two AI products feel very different, the difference usually comes from one of three things: the model, the harness, or the scaffolding around both. Being able to tell them apart helps when you choose coding tools for your engineering org, compare AI vendors, or explain why a tool someone tried six months ago feels different now.

    Chapter 3

    Inside the agent

    Up to this point you’ve worked with models from the outside — using harnesses, swapping models behind them, comparing them. The next three codelabs go inside the harness itself.

    05Harness from scratch

    Build a small ReAct-style harness with two tools (web_search and get_local_time). Claude writes the code; you read it. The point is to see that a harness is roughly a while loop with some glue around it. Codelab #4 introduced the abstraction; this one makes it concrete.

    Why it matters for a CEO When a vendor, or your own product team, pitches an “AI agent”, you’ll be able to tell which parts are commodity plumbing (the agent loop, tool calling) and which parts might be differentiated (the tools, the data, the workflow knowledge). That tells you where to invest and what to ask.

    06MCP server build

    Wrap the National Weather Service API in an MCP server and connect it to Claude. Watch the same prompt go from a vague guess to a real forecast. Now that you’ve built a harness with tools by hand, MCP is the standard way other harnesses pick up new tools.

    Why it matters for a CEO MCP is how AI tools get connected to your CRM, ticketing system, data warehouse, and internal docs. Most “can we connect Claude to X?” conversations come down to whether X already has an MCP server and whether someone could build one in an afternoon. There’s a strategic question on the other side too: should your product expose an MCP server so your customers’ agents can use it?

    07Memory & retrieval

    Implement two or three retrieval patterns on the same corpus — vector RAG, markdown-wiki, optionally graph RAG. Compare quality, latency, and setup cost. Tools let an agent do things; retrieval lets it look things up. Most useful business workflows need both.

    Why it matters for a CEO Most “AI over our docs” or “ask your data” features, whether in your product or on an internal knowledge base, succeed or fail on retrieval, not on the model. The right pattern depends on the shape and size of the content. It’s worth understanding before you fund a retrieval project or sign up for a vendor’s knowledge-base product.

    Chapter 4

    Packaging and platforms

    Codelabs 1 through 7 cover the same building blocks: model, harness, tools, memory. The next two are about packaging your work and running it elsewhere — different platforms, different file formats, mostly the same underlying abstractions.

    08Plugins & portable agents

    Build a small Claude plugin with one agent and one skill. Watch the agent run in its own context window, separate from your main session. Then translate the agent definition into Codex (OpenAI’s CLI) and run the same task there. The lock-in between harnesses for skills and agents turns out to be small — the wrapper file is vendor-specific, but the agent itself moves with a short translation.

    Why it matters for a CEO This is how a useful workflow your team builds in Claude Code gets packaged so everyone can use it. It also tells you how much “built on Anthropic” (or OpenAI, or Gemini) lock-in is actually worth, both when a vendor pitches you and when your own team picks a platform. It’s usually a lot less than people assume.

    09Hermes Agent deep-dive

    Spin up Hermes, dispatch a long-running task, walk away from your computer. Compare its trajectory to Claude Code on the same task. Codelab #8 packaged an agent so it could move across harnesses; this one explores a different dimension — interactive sessions you supervise versus async tasks you check back on later.

    Why it matters for a CEO Interactive agents you supervise and asynchronous agents you hand a task to and check on later suit different kinds of work. As your teams start handing work to agents, it helps to know from experience which mode fits which job, rather than relying on vendor decks.

    Chapter 5

    Compose and measure

    The last two codelabs do two different things. The first composes multiple agents into one workflow. The second teaches you how to decide whether a workflow is good enough to use.

    10Multi-agent SDLC pipeline

    Five Claude Code subagents — Planner, Builder, PR-opener, Reviewer, Merger — running a PRD-to-PR pipeline on a small real task. Cost meter open. You leave the computer for 20 minutes and come back to whatever they produced. This puts the earlier codelabs together, with a real cost attached.

    Why it matters for a CEO A small internal tool built unsupervised for $5–50 is the kind of software development your engineering org is moving toward. Doing it once shows you the cost-to-output ratio, which tasks are specified well enough to hand to agents, and why code review and QA become the bottleneck. Those are useful things to understand before your next planning or headcount conversation.

    11Evals as a workflow

    Build a small eval suite for a real workflow, scored against a rubric. Support-ticket triage is the default. Run the same suite across three models. Rank them. The point is that without an eval, every model-choice or prompt-tweak conversation is a vibe; with an eval, you have a number.

    Why it matters for a CEO Any AI feature you ship to customers, and any vendor claiming “our AI resolves 60% of tickets”, should come with an eval. The harness is small. Writing the rubric is the hard part, and that is a product and leadership job, not only an engineering one. It’s worth doing once yourself before you ask your teams to do it.

    Open-source models & local hosting

    Time
    60–90 minutes
    Difficulty
    Beginner
    Prerequisites
    Claude Code installed, ~10 GB free disk
    You will need
    Hugging Face account, Fireworks account

    Why this matters

    You’ve almost certainly used a language model through a chat box — Claude.ai, ChatGPT, Gemini. Those are closed models running on someone else’s servers, billed by the token. There is a parallel universe of open-source models that you can download and run on your own laptop, or on a cheap hosted endpoint, for a fraction of the cost.

    You don’t need to become an open-source-model expert. But the moment you’ve done this once, your mental model of “how AI gets bought and built” gets meaningfully sharper. You’ll know, viscerally, that “the model” and “where the model runs” are two separate choices — which matters when you’re evaluating a vendor, sizing inference costs in your own product, or answering a customer who wants to know whether their data ever leaves their environment.

    What you’ll do

    • Pull a small open-source language model from Hugging Face onto your laptop and get it answering prompts.
    • Call a much larger frontier model (Kimi K3) on a hosted Fireworks endpoint.
    • Send the same 5 prompts to both and compare latency, cost, and quality.
    • Walk away with a real point of view on when small-and-local is enough and when you reach for a frontier model.

    What you’ll actually learn

    The exercise is the surface. The real takeaways:

    • How to download and run an open-source model on your laptop. The mechanics — CLI, Hugging Face, choosing a runtime, getting a first response back. This is the foundation everything downstream relies on.
    • How to estimate whether a model fits on a given machine. Parameter count × bytes per parameter ≈ memory needed. A 7B model at 4-bit quantization is ~3.5 GB; a 70B is ~35 GB; a 405B is firmly past laptop territory. This math comes up every time you’re evaluating whether something is doable on the hardware in front of you.
    • Hand the agent the CLI. When you meet any new platform, the move is to install its command-line tool and let Claude drive it. You don’t click through websites.
    • You can ask Claude to explain itself. Every term, every error, every weird output — paste it back and ask. This is the loop.

    The memory math (and what you’re not running)

    Before you download anything, it’s worth knowing why the list above stops around 9B. The math is roughly: parameter count × bytes per parameter ≈ memory needed just to load the weights.

    • At FP16 (the default precision): ~2 bytes per parameter. A 7B model loads in roughly 14 GB of RAM.
    • At 4-bit quantization: ~0.5 bytes per parameter. The same 7B model now fits in ~3.5 GB.
    • Add a few GB on top for activations, the KV cache (which grows with context length), and the OS.

    For scale, here’s where some well-known large models sat at the time of writing (the names will have moved on; the math won’t):

    • gpt-oss-120b (OpenAI) — 117B total parameters, ~5B active per token (mixture-of-experts). It ships pre-quantized and fits on a single 80 GB GPU. A workstation, not a laptop.
    • Mistral Medium 3.5 — 128B parameters, all of them active on every token (a “dense” model). ~256 GB at FP16, ~64 GB quantized.
    • Llama 3.1 405B (Meta) — from 2024, but still the largest dense open base model; ~800 GB at FP16, ~200 GB quantized. Datacenter territory.
    • DeepSeek V4 Pro — 1.6T total parameters, ~49B active per token (mixture-of-experts). All weights still need to live in memory, even though only ~49B fire on any given token.
    • Kimi K3 (Moonshot) — roughly 2.8T total parameters, ~104B active. The model you’ll call on Fireworks in Milestone 3.
    • Frontier closed models (the current top models from Anthropic, OpenAI, and Google) — exact sizes aren’t disclosed, but the consensus is trillions of parameters, MoE. Datacenter territory regardless.

    The model you’re about to run on your laptop is roughly 100× to 1,000× smaller than the frontier. That’s worth feeling. It’s also why this codelab’s comparison at the end isn’t fair in absolute terms — it’s showing you the shape of a trade-off, not the limit of what local models can do.

    Model routing

    Time
    60–90 minutes
    Difficulty
    Beginner–Intermediate
    Prerequisites
    Claude Code installed, comfortable storing an API key
    You will need
    OpenRouter account, optional Fireworks & Anthropic & OpenAI keys

    Why this matters

    The dominant mental model for AI is “pick a model and use it for everything.” That’s a beginner’s choice. Behind every serious production AI system is a quieter decision: which model gets which call? A one-line factual lookup goes to something tiny and nearly free. A messy reasoning question goes to a frontier model that costs a hundred times more. The agent “shops” for the right model on every prompt, the same way you’d put a senior engineer on the gnarly outage and a junior one on the typo fix.

    The economic gap is wider than most people think. The cheapest hosted models on the market run around $0.00003–$0.0003 per response. A top-tier model costs about $0.01–$0.03 per response, and $0.05–$0.15 once it “thinks” before answering (thinking tokens are billed like output). That’s a spread of 1,000x or more. If you’re only using the expensive one, you’re paying a steep premium on every easy question. Routing is how grown-up systems handle that — and you’re going to build one in the next 90 minutes.

    What you’ll do

    • Set up an OpenRouter account — the single API key that fans out to a hundred models behind one endpoint.
    • Configure four routes pointing at very different models: a small/cheap one, a mid-tier one, a frontier reasoning model, and an Anthropic model.
    • Write a small router that decides — per prompt — which model to send the call to, based on rules you specify.
    • Run a 5-prompt eval and watch the router pick a $0.0003 model for “What’s the capital of France?” and a $0.05 model for a hard reasoning question.
    • Leave with a working prototype and an opinion about how to set the rules.

    What you’ll actually learn

    The exercise is the surface. The real takeaways:

    • You don’t have to commit to one model. Routing is a real architectural choice, not an exotic optimization. Production systems do this by default.
    • The agent can shop for the cheapest answer that meets the bar. Once you’ve seen it happen prompt-by-prompt, you’ll start noticing the places in your product and your team’s tooling where someone is paying frontier-model prices for trivial work.
    • Single-model architectures are a beginner’s choice. “Which model are we using?” is the wrong question. “What’s our routing policy?” is the right one.

    Milestone 3 · Write the router

    ~20 min

    Goal

    A function — call it route(prompt) — that takes a prompt and returns the answer from the cheapest model that meets a quality bar. It should print, for every call, which tier it picked and why.

    The routing logic, in plain English

    There are two reasonable strategies. Both are worth knowing.

    1. Classify first. Use a cheap model to look at the prompt and decide what kind of question it is (simple lookup / mid-complexity / hard reasoning). Then send it to the matching tier. One extra call, but predictable.
    2. Cheap first, escalate. Send every prompt to tiny first. Have a cheap model judge whether the answer looks confident and complete. If not, escalate to mid. If still not, escalate to frontier. Slower in the worst case, but cheaper on average.

    Pick one for now. Classify-first is easier to reason about for a first build. Cheap-first / escalate is closer to how real systems work but has more moving parts. Either one teaches the lesson.

    Nudges

    • Don’t hand-write the classifier. Ask Claude to draft the classifier prompt — “given a user prompt, return one of simple / medium / hard and a one-line reason.” Use your tiny model for the classifier itself — the routing decision should not cost more than the answer.
    • Have the router print its work. Every call should produce one line of output like [router] simple → tiny ($0.00012) — “factual lookup, no reasoning needed”. The whole point of this codelab is that you watch the decisions happen.
    • Don’t over-engineer. Three tiers, three rules, ten lines of code. If Claude wants to write fifty lines, tell it to cut.

    Suggested prompts

    Paste into Claude

    Write a route(prompt) function that does the following: (1) calls the tiny model with a classifier prompt to decide whether the user’s question is simple, medium, or hard, (2) sends the actual prompt to tiny, mid, or frontier based on that, (3) prints a one-line trace showing which tier was picked, why, and what each call cost. Keep it short and readable — I want to be able to look at this code and understand it.

    Paste into Claude

    Test the router on three prompts: “What’s the capital of France?”, “Write a three-sentence cover note for a quarterly board update,” and “A SaaS company has $40M ARR, 115% net revenue retention, and adds $8M of new-logo ARR per year (assume it lands at year-end). Estimate ARR at the end of year 3. Show the math.” Print the router’s decision for each.

    Why this works

    You just built a tiny version of what every serious production AI system does. The classifier is itself an LLM call — a model judging which model the “real” call should go to. That feels recursive and weird the first time you see it. It’s also exactly right. Cheap models are great at routing decisions even when they’d be lousy at the actual reasoning.

    Milestone 5 · Tune the rules and break the router on purpose

    ~15 min

    Goal

    You change something about the routing logic — the classifier prompt, the tier-to-model mapping, or the bar for escalation — and watch the eval results change. You walk away with an opinion about how you’d set the policy for a real workflow.

    Things worth trying

    • Tighten the classifier. Make the classifier prompt stricter — “only classify as hard if the question requires multi-step quantitative reasoning.” Re-run the eval. Did anything move down a tier? Did quality suffer?
    • Add a domain rule. Hard-code one override — e.g. “if the prompt mentions ARR, NRR, or CAC, route to frontier regardless of the classifier.” Useful pattern for production: rules over judgment for known-important cases.
    • Swap the mid model. Try a different mid-tier model (a different family — if you’ve been on GPT, try a Claude or Gemini equivalent). Re-run. Notice that “mid” is a category, not a model.
    • Break it intentionally. Force every prompt to tiny and re-run. See what falls apart. That’s your lower bound. Now you know what the routing is actually buying you.

    Routing policy is not a one-time configuration — it’s a knob you tune as you learn what your real workload looks like. The override-on-keyword pattern (rules first, judgment second) is how almost every production router actually works. Pure LLM-judged routing is fragile in obvious ways; pure rule-based routing can’t handle novelty. The mix is what works.

    60–90 minutes

    Why this matters

    Inference cost is the most volatile line in any AI vendor pitch, and in your own AI roadmap. The same prompt can be ten times cheaper — sometimes a hundred times cheaper — depending on which model you send it to, and the gap rarely tracks the quality gap. Most leadership teams have a vague sense of this and no first-hand evidence. By the end of this exercise you’ll have evidence: a spreadsheet with ten models, ten prompts, and real numbers for cost, speed, and how good each answer looked.

    The numbers themselves are the smaller prize. The bigger prize is that you’ll have a benchmark you can rerun in six months without redoing any of the setup work. The landscape moves fast — a model that was twice the price of a competitor today will be a third of the price next quarter. Having your own personal yardstick beats reading anyone else’s benchmark, because your prompts are the ones you actually care about.

    What you’ll do

    • Create an OpenRouter account and an API key — one key that gets you to roughly every commercial model on the planet.
    • Hand the key to Claude and let it write a benchmark script that fires ten prompts drawn from running a software company at ten different models.
    • Capture tokens-in, tokens-out, cost, and latency for every single call into a CSV you can keep.
    • Turn the CSV into a one-page markdown summary that ranks the models on cost, speed, and a spot-check of quality.
    • Walk away with a personal benchmark you can rerun in six months to see how the market has shifted.

    What you’ll actually learn

    The exercise is the surface. The real takeaways:

    • Cost varies wildly across models for the same work. Not 20% — sometimes 100×. The cheapest competent model is almost never the one in the headlines.
    • Tokenizers matter. The same prompt is a different number of tokens to different providers, because they each chop text up their own way. The same paragraph can cost 30% less to send to one model than another before either has produced a single word of output.
    • You can run cheap evals. The whole exercise costs about the price of a coffee. Once you’ve done it once, comparing models stops feeling like a research project and starts feeling like a habit.

    Why these flags

    --permission-mode auto lets Claude work without asking you to approve every command, file write, or install, which is the let-Claude-drive feeling these codelabs depend on. In auto mode, a second safety model reviews each action before it runs. Routine work in your folder goes through, and risky moves get stopped and handed back to you: piping a script from the internet into your shell, sending data to an unknown endpoint, touching things outside the task. When it stops and asks, read the request and decide. That pause is the guardrail working. In recent versions auto mode is already the default, so the flag just makes it explicit.

    Don’t reach for --dangerously-skip-permissions. You’ll see it in older tutorials. It turns every check off, and Anthropic’s docs reserve it for isolated containers and VMs. If auto mode isn’t available on your account, use --permission-mode acceptEdits instead and approve commands as they come up. Either way, follow the guardrails in Start here: a sandbox machine, no company data, small credit limits.

    --effort max tells Claude to think as hard as it can on every step. During a learning exercise you want the strongest version of the model, not the cost-saving one. It does use your plan’s limits faster. If you hit a limit, drop to --effort high.

Claude Code does exactly this, just with more tools (Read, Write, Bash) and more polish. Cursor does this. Hermes does this. Every agent product is variations on these 50 lines.

    MCP server build

    Time
    60–90 minutes
    Difficulty
    Beginner
    Prerequisites
    Claude Code installed, Node.js or Python on your machine
    You will need
    Nothing else — the National Weather Service API is free and unauthenticated

    Why this matters

    Everyone’s favorite complaint about Claude is some version of “it doesn’t know about our stuff.” It doesn’t know which accounts are up for renewal in your CRM. It can’t pull a customer’s open tickets from Zendesk or Jira. It can’t query the usage tables in your data warehouse or find the right page in your internal docs. That gap — between “Claude can chat” and “Claude can act on your systems” — feels enormous from the outside. It isn’t.

    The bridge is called MCP (Model Context Protocol). Think of it as the universal plug: any tool, API, or data source on one side; any AI model on the other; a simple shared standard in the middle. If a system has an API, you can wrap it in an MCP server in an afternoon and Claude can use it. In the next 60–90 minutes you’re going to build one yourself for a public weather API, and the experience of watching Claude go from “vague guess” to “precise answer with real data” will tell you everything you need to know about how your team could connect Claude to your CRM, ticketing system, data warehouse, or internal docs, and what it would take for your own product to plug into your customers’ AI tools the same way.

    What you’ll do

    • Ask Claude a specific weather question with no tools connected and notice that the answer is vague or quietly made up.
    • Have Claude scaffold an MCP server that wraps the free National Weather Service API.
    • Define two or three tools on that server — get_forecast, get_marine_forecast, get_hourly_forecast — without writing the code yourself.
    • Wire the server into Claude Code’s MCP configuration and confirm Claude can see the new tools.
    • Re-run the original question, watch Claude actually call the API, and compare the two answers side by side.

    What you’ll actually learn

    The weather server is the surface. The real takeaways:

    • MCP is just a protocol, not magic. It’s a tiny JSON-RPC convention for “here are the tools I have; here’s how to call them.” Once you’ve seen one, you’ve seen them all.
    • Anything with an API can become an MCP server. Public APIs, internal APIs, a script that hits a database — same pattern. The hard part is almost never the wrapping; it’s deciding which 2–3 tools are actually useful.
    • Tools are the bridge from “chat” to “act.” Once Claude has the right tools, the conversation stops being about hypotheticals and starts being about real outputs. That’s a different posture.

    2. Open a terminal in that folder and start Claude Code with this exact command: 
      claude --permission-mode auto --effort max
    Why these flags

    --permission-mode auto lets Claude work without asking you to approve every command, file write, or install, which is the let-Claude-drive feeling these codelabs depend on. In auto mode, a second safety model reviews each action before it runs. Routine work in your folder goes through, and risky moves get stopped and handed back to you: piping a script from the internet into your shell, sending data to an unknown endpoint, touching things outside the task. When it stops and asks, read the request and decide. That pause is the guardrail working. In recent versions auto mode is already the default, so the flag just makes it explicit.

    Don’t reach for --dangerously-skip-permissions. You’ll see it in older tutorials. It turns every check off, and Anthropic’s docs reserve it for isolated containers and VMs. If auto mode isn’t available on your account, use --permission-mode acceptEdits instead and approve commands as they come up. Either way, follow the guardrails in Start here: a sandbox machine, no company data, small credit limits.

    --effort max tells Claude to think as hard as it can on every step. During a learning exercise you want the strongest version of the model, not the cost-saving one. It does use your plan’s limits faster. If you hit a limit, drop to --effort high.

    Milestone 3 · Add the tools

    ~20 min

    Goal

    Two or three real tools exposed by your server, each one wrapping a National Weather Service endpoint. Claude designed them, Claude wrote them, you reviewed them.

    Pick from this shortlist

    The NWS API exposes a lot. Don’t try to wrap all of it. Two or three of these is plenty:

    • get_forecast(lat, lon) — a 7-day general forecast for any US coordinates. The bread-and-butter tool.
    • get_marine_forecast(zone) — coastal and offshore marine forecasts by NWS zone code (e.g., ANZ230 for Boston Harbor). This is the one that makes the “Boston marine” question dramatic.
    • get_hourly_forecast(lat, lon) — hour-by-hour temperature, wind, precipitation chance for the next 7 days.

    • Hand the shortlist to Claude and ask it to pick two or three. Have it explain the design choice — which endpoints, what arguments, what each tool returns. This is where the LLM-craft is.

    Milestone 3 · The markdown-wiki pattern

    ~15 min

    Goal

    The same five questions, answered by Claude Code itself, with no embeddings, no vector store, and no Python script — just file-system tools pointed at the corpus/ folder. This is a version of what Andrej Karpathy called the “LLM wiki” pattern (April 2026), and it’s deceptively powerful.

    Nudges

    • You’re already in Claude Code. It already has read access to the folder. There is nothing to install. Ask Claude to do a little prep work first: add a top-level INDEX.md that lists every customer, its segment, its industry, its ARR, and its renewal date, so Claude has a fast way to triage which files to open.
    • For each question, ask Claude to show its work — which files it opened, in what order, and why. This makes the comparison with vector RAG honest.
    • Resist the urge to over-engineer. The whole point is that a structured folder + a good agent is sometimes all you need. Don’t add fancy tooling.

    Suggested prompts

    Paste into Claude

    I want to try a different retrieval pattern. Instead of embeddings and a vector store, I want you — Claude Code, with your file tools — to be the retrieval system.     Paste into Claude

    Why this works

    You’re using the agent itself as the retrieval engine. Its “index” is your folder structure plus the INDEX.md you just had it write. It doesn’t need embeddings because it can read. For small, well-organized corpora — which is what a surprising number of internal-knowledge use cases, and even some per-customer product features, actually are — this approach is shockingly hard to beat. It also has a property vector RAG doesn’t: it can reason about which files to open, instead of just matching tokens.

    ~15 min

    Goal

    Milestone 5 · Five questions, three pipelines, one verdict

    ~20 min

    Goal

    The five questions

    What you actually learned

    Surface lesson. You built two or three different retrieval pipelines over the same 20-file corpus and ran the same five questions through each. You saw, with your own eyes, that vector RAG can confidently miss the obvious; that a well-organized folder of markdown files and an agent with file tools can be startlingly good; and that graph RAG is powerful for relationship questions but expensive to stand up.

    Hidden curriculum. “RAG” is not a thing you buy — it’s a design space. The decision “how should the agent find things” is upstream of “which model do we use,” and getting it wrong is the cause of more disappointing AI features and stalled internal knowledge-base projects than any model choice ever has been. You also learned that the cheapest option in a design space is often the best one to start with — you can always graduate to vector or graph RAG once you’ve outgrown a folder of markdown files, but most people who buy vector databases never actually needed one.

    Where this shows up in your company. Most “AI over our docs or data” features in your product succeed or fail on retrieval, not on the model. When your product team demos one, ask what retrieval pattern sits behind it, how they measure retrieval quality separately from answer quality, and what each query costs in embeddings, tokens, and infrastructure. Next time a vendor pitches you a six-figure “AI knowledge base” for support or sales enablement, ask “what retrieval pattern are you using, and why is it the right one for a corpus this size?” And next time someone says “we need RAG over our internal wiki,” you’ll know the first move is to get the content into a clean, consistently structured folder and point an agent at it — and only then ask whether you need anything heavier.

    • Chroma or LlamaIndex won’t install. Ask Claude to check your Python version and switch to a virtual environment. If a dependency is fighting you, ask Claude to pick a leaner alternative — there are several local vector stores and they’re mostly interchangeable for this exercise.

    1. Claude Code installed and working, signed in with an Anthropic API key that has billing enabled. (Free trial credits will run out fast in this exercise — that’s by design.) If your Claude plan doesn’t give you Anthropic Console access (common on company plans), create a personal Console account for this lab. You can run it on a Claude subscription instead, but then usage counts against your plan limits and you may not get the per-run dollar figure that’s the point of this lab. Use a personal account with a small spending limit, not company billing, unless your company has approved it.
    2. The GitHub CLI (gh) installed and authenticated.
    3. A scratch GitHub repository on your personal account that you don’t mind cluttering with experimental PRs. Not a repo in your company’s GitHub org, and no company code in it. A fresh empty repo is perfect. If you don’t have one, we’ll have Claude create one in Milestone 2.
    4. A small real-ish feature in mind. Not “rebuild your billing system.” Something like: “a tiny web tool that takes a CSV of product usage events and renders a sortable table of the most- and least-active accounts” or “a script that compares two exports of your pricing page or price book and prints what changed.” Real enough that you’d be glad to have it. Small enough that one engineer could finish it in an afternoon. Any sample data the agents need should be synthetic or public, never real customer data.

    Open Claude Code the right way

    Same opening as every codelab in this series:

    1. Make a new folder somewhere obvious on your machine — Desktop or Documents — and name it codelab-10-multi-agent-sdlc. Everything you build today lives inside it.
    2. Open a terminal in that folder and start Claude Code with this exact command: 
      claude --permission-mode auto --effort max
    Why these flags

    --permission-mode auto lets Claude work without asking you to approve every command, file write, or install, which is the let-Claude-drive feeling these codelabs depend on. In auto mode, a second safety model reviews each action before it runs. Routine work in your folder goes through, and risky moves get stopped and handed back to you: piping a script from the internet into your shell, sending data to an unknown endpoint, touching things outside the task. When it stops and asks, read the request and decide. That pause is the guardrail working. In recent versions auto mode is already the default, so the flag just makes it explicit.

    Don’t reach for --dangerously-skip-permissions. You’ll see it in older tutorials. It turns every check off, and Anthropic’s docs reserve it for isolated containers and VMs. If auto mode isn’t available on your account, use --permission-mode acceptEdits instead and approve commands as they come up. Either way, follow the guardrails in Start here: a sandbox machine, no company data, small credit limits.

    --effort max tells Claude to think as hard as it can on every step. During a learning exercise you want the strongest version of the model, not the cost-saving one. It does use your plan’s limits faster. If you hit a limit, drop to --effort high.

    Milestone 1 · Draft a real PRD with Claude

    ~15 min

    Goal

    A one-to-two-page PRD.md in your folder that describes the feature clearly enough that a stranger could build it. No code yet — just the spec.

    Nudges

    • A PRD (product requirements document) is the same thing a product manager would hand to an engineer. It says what to build and why, not how. If the term is new, ask Claude to explain it in plain English.
    • Don’t try to write the PRD yourself and then hand it over. Tell Claude what you want, let it draft, and push back on anything vague. The quality of the PRD is the single biggest lever on whether the agents produce something useful in Milestone 4.
    • Specifically force the PRD to include: the user, the problem, the input format, the output format, three concrete acceptance criteria, and what’s explicitly out of scope. The “out of scope” section is the one that saves you money later.
    • Keep it small. If your feature has more than five acceptance criteria, cut it in half. You can always do a second run.

    Suggested prompts

    Paste into Claude

    Help me write a PRD for a small feature. Here’s the rough idea in one sentence: [your idea]. Ask me clarifying questions — user, inputs, outputs, what “done” means — until you have enough to write a tight one-to-two-page PRD. Save it as PRD.md in this folder. Make sure it has a clear “out of scope” section so the agents don’t go off and gold-plate.

    Paste into Claude

    Read the PRD back to me. Is there anything vague or contradictory that a junior engineer would have to guess about? If yes, fix it. Imagine you’re going to walk away and a different agent will build this from PRD.md alone, with no access to me.

    Why this works

    Every dollar you spend in Milestone 4 traces back to how clear this document is. Ambiguity in a PRD becomes loops and rework when the agents are running unsupervised — and loops cost money. A tight spec is the cheapest thing you’ll do today.

    ✓ You have a PRD.md in your folder. You’ve read it back and you genuinely believe a stranger could build the feature from it without asking you anything.

    Milestone 2 · Configure the five-agent pipeline

    ~20 min

    Goal

    Five named subagents defined inside your Claude Code project, each with its own role description and the right tools. A fresh GitHub repository connected to the folder. A short orchestrator prompt that hands the PRD to the planner and tells the planner to hand off when ready.

    The roster

    You’re building a tiny SDLC (software development lifecycle) on your laptop. Each role does one job:

    • Planner. Reads PRD.md. Writes PLAN.md — the file structure, the implementation steps, the testing approach. Does not write any product code.
    • Builder. Reads PLAN.md. Writes the actual code on a feature branch. Runs tests locally if any exist.
    • PR-opener. Commits, pushes the branch, and opens a pull request via gh with a clear title and description that references the PRD.
    • Reviewer. Reads the diff on the PR and leaves substantive line-level comments. Plays the adversary — not a rubber stamp. Asks the Builder to revise if the diff doesn’t meet the PRD’s acceptance criteria.
    • Merger. Reads the review thread. If criteria are met and no blocking comments remain, merges the PR. If not, kicks it back to the Builder with a written reason.

    Nudges

    • You don’t define these by hand. Ask Claude Code to create them as subagents. Each one is a small markdown file in .claude/agents/ that Claude writes for you. Each agent should get a system-prompt-style role description and a restricted set of tools (the Planner doesn’t need gh; the Reviewer doesn’t need to write files).
    • If a Claude Code skill applies to a role (e.g., a code-review skill, a PRD-writing skill), attach it. Skills sharpen the agent without you having to write a 400-line prompt.
    • The Reviewer is the most important agent to get right. If it’s too soft, the loop closes too fast and you ship slop. Push Claude to write a Reviewer prompt that explicitly tries to break the diff.
    • For the GitHub repo: ask Claude to create a fresh empty one on your personal account using gh repo create (private is fine), connect your folder to it, and push an initial commit. Don’t do this in a browser, and don’t point it at your company’s GitHub org.

    Suggested prompts

    Paste into Claude

    I want to set up five subagents inside this Claude Code project: Planner, Builder, PR-opener, Reviewer, and Merger. For each one, write a tight role prompt that describes its single responsibility, what files it reads, what files it writes, and which tools it’s allowed to use. Use the /agents command (or whatever the right mechanism is in this version of Claude Code) to actually create them. Walk me through what you’re doing as you go.

    Paste into Claude

    Now connect this folder to a fresh GitHub repository under my personal account (not a company org) using gh. Don’t open a browser. Make the initial commit with PRD.md in it, push to main, and confirm the remote is wired up.

    Paste into Claude

    The Reviewer is the agent I’m most worried about. Sharpen its prompt so it actively tries to find problems — missing edge cases, things outside the PRD’s scope, code that technically works but a human would never write. Reject “LGTM” behavior. I’d rather it kick the Builder back twice than rubber-stamp.

    Heads up

    If you’ve never seen subagents before, this is the moment where the abstraction clicks. They’re not separate logins or separate accounts — they’re separate roles with their own context windows and their own tools, orchestrated by your top-level Claude Code session. Ask Claude to explain how the handoffs work if it feels mysterious. The right metaphor is “five colleagues in a Slack channel,” not “five tabs in a browser.”

    ✓ Asking Claude “which subagents are defined in this project?” lists your five agents, and you can see their files in .claude/agents/. The folder is connected to a GitHub repo. PRD.md is committed and pushed. You haven’t written any product code yet — that’s on purpose.

    Milestone 4 · Walk away

    ~20 min (mostly not at your desk)

    Goal

    You press Enter on the orchestrator prompt, watch the first thirty seconds to make sure the Planner actually starts working, and then physically leave your desk for twenty minutes. Get a coffee. Take a walk. Go to a meeting. The pipeline either finishes or doesn’t while you’re gone.

    Nudges

    • This sounds soft. It is not soft. The point of leaving is to break the chat-app reflex of staring at the screen and intervening. Unsupervised means unsupervised. If you stay, you will start “helping” and the lesson is lost.
    • Set a timer for 20 minutes. Don’t check your phone for “status.” The agents are either fine or they’re not, and you watching won’t change anything.
    • If something genuinely catastrophic happens and you need to kill it, Ctrl-C in the Claude Code terminal stops the run. You will still owe for the tokens already spent. Stopping early is fine; pretending you can micromanage from your phone is the failure mode.
    • If you absolutely can’t leave (open-plan office anxiety is real), at least turn the monitor away from you. Read a book on your phone. Do anything except input.

    Suggested prompts

    Paste the orchestrator prompt you wrote in Milestone 3 into Claude Code. Hit Enter. Watch for thirty seconds. Then stand up.

    Why this works

    You can’t learn the “AI as a teammate” mental model while you’re acting like AI’s manager. The whole point of unsupervised execution is that your attention is not in the loop. The first time you do this, your hands will itch. Sit on them. The mental shift is the lesson, and it only happens by force.

    ✓ You left the desk. You came back. The terminal shows either a finished pipeline, a stuck agent waiting on you, or an error. Whichever it is, you’re now ready for Milestone 5.

    Milestone 5 · Inspect the work and the bill

    ~20 min

    Goal

    You have a real answer to three questions: Did it ship? Was the work any good? How much did it cost? You compare your sticky-note guess from Milestone 3 to the actual number. You can articulate at least one moment where the agents disagreed or one place the Reviewer caught the Builder.

    Nudges

    • Start with /usage. Look at it. Subtract your Milestone 3 baseline. That’s what the run cost. Compare it to your sticky-note guess.
    • Open the pull request on GitHub. Read it like you’d read a junior engineer’s PR — what does the diff actually do, does it match the PRD, is anything weird?
    • Read the Reviewer’s comments and the Builder’s replies. This is where the most interesting learning lives. Did they argue? Did the Reviewer push back? Did anything get fixed because of the review? If the Reviewer rubber-stamped everything, that’s a data point about your prompt — not about the model.
    • Now ask the most important question out loud: would you have built it faster, better, or cheaper yourself? Be honest. Sometimes the answer is yes — and that’s the lesson.

    Suggested prompts

    Paste into Claude

    Run /usage and tell me what this run cost — just the delta since Milestone 3, not the whole session. Then open the PR via gh and summarize for me: did the pipeline complete, did the Merger actually merge, what did the diff change, and where (if anywhere) did the Reviewer push back on the Builder?

    Paste into Claude

    Build me a small table comparing this run to a hypothetical “I did it myself” baseline. Columns: time elapsed, dollars spent, lines of code produced, would I trust the output without reading it. Fill in the agent-pipeline row honestly. Leave the “myself” row blank for me to fill in based on my own estimate.

    The comparison

    This is the moment the codelab is built around. Sit with the side-by-side. Pick a number, pick a quality judgment, and dictate a one-line conclusion to Claude — have it add the line to the bottom of your results file. Examples participants come back with:

    • “$6.40 and a working PR. I’d have spent 90 minutes. I’m using this on every internal tool from now on.”
    • “$31 and a PR that almost works but ignored half the acceptance criteria. My PRD was the problem.”
    • “$18 and the Reviewer caught a real bug the Builder introduced. I’d trust this for prototypes, not for anything I’d ship.”

    All three answers are correct. The one you land on is your data point.

    ✓ You know the exact dollar cost of the run, you’ve read the PR, you can name one moment the Reviewer pushed back (or honestly say it didn’t), and you have a one-line conclusion you could repeat to your CTO.

    What you actually learned

    Surface lesson. You wrote a PRD with Claude, set up five subagents with distinct roles and tools, kicked off an unsupervised pipeline that produced a real pull request, watched the cost meter run, and inspected both the artifact and the bill. Almost no one has done this end-to-end before today.

    Hidden curriculum. You experienced — in your hands, with your money — that AI work has a unit cost, that unsupervised execution is a real operating mode, and that the leverage point is the spec, not the prompt. A clear PRD is worth ten clever prompts. The agents are linear; the leverage is upstream. You also felt the discomfort of leaving the desk while a process runs, which is exactly the discomfort you’ll need to get over to use this mode at scale.

    Where this shows up in your company. What you just ran on your laptop is a toy version of what agentic software development looks like inside your engineering org. Four questions are now concrete for you:

    • Cost per PR or per task. You now have a real number for one small feature. Ask your CTO what the equivalent number is across the team, how it compares to an engineer-hour, and who is watching the meter when a hundred of these run a day.
    • Which tickets are agent-ready. The run lived or died on the PRD. In your backlog, that’s the difference between a Jira ticket with crisp acceptance criteria and one that says “make onboarding better.” Ask what share of your tickets are specified well enough to hand to an agent, and who writes them.
    • Review and QA become the bottleneck. The agents produced code faster than you could read it. At team scale, the constraint moves from writing code to reviewing, testing, and safely shipping it. Ask where PRs are queuing today and whether your test coverage is good enough to trust code nobody wrote by hand.
    • Team shape. If agents do more of the building, the scarce people are the ones who can write a tight spec, review hard, and own the architecture. That changes your hiring mix, your senior-to-junior ratio, and how you grow junior engineers who no longer learn by writing the easy tickets.

    Underneath all four: not every piece of work is PRD-able, and learning which ones are is more valuable than the pipeline itself.

    • PRD-able: Internal tools and small utilities. Recurring data-transformation scripts. Well-scoped bug fixes and small features with crisp inputs and outputs. Internal dashboards (a weekly NRR or churn view, say) with well-defined acceptance criteria. Anything where you can write down “done looks like X” in three bullets.
    • Not PRD-able (yet): Anything where the judgment is the deliverable — a board memo, a pricing or reorg decision, a sensitive customer escalation email. Anything where the inputs aren’t crisp or the standard of “done” lives in your head or your head of product’s. Anything with regulatory, security, or customer-data stakes where unsupervised execution is inappropriate regardless of model quality.

    The skill you just started building is knowing the difference. That’s the one to keep practicing, and the one to expect from your engineering leaders.

    If you got stuck

    The single most useful prompt in this entire codelab — keep it in your back pocket:

    Paste into Claude

    Here’s exactly what I saw on my screen: [paste]. Explain in plain English what’s going on, then tell me what to try next. If you can fix it yourself, do that. If we’re burning tokens in a loop, stop the run first.

    Common stuck points:

    • The agents are looping and the meter is climbing fast. Stop the run with Ctrl-C. Ask Claude to look at the trace and tell you which two agents are bouncing the work back and forth. The fix is almost always a clearer handoff condition in one of the prompts, or a tighter acceptance criterion in the PRD.
    • The Reviewer rubber-stamped a bad PR. That’s a prompt problem, not a model problem. Strengthen the Reviewer’s role description — explicitly forbid “LGTM” with no substantive comments, and require it to list at least two things it considered rejecting. Then run again.
    • The Builder went way out of scope. Your PRD’s “out of scope” section was too short. Add specifics. “Do not add tests beyond the three listed.” “Do not introduce new dependencies.” Specificity beats hope.
    • The pipeline stalled and a subagent is waiting on me. Read what it’s asking. If it’s a clarifying question that should have been answered in the PRD, answer it now and then go back and update the PRD for next time. If it’s a permission/credential issue, fix that and resume. If it stopped on a permission prompt for a git or gh command, approve it, then ask Claude to add that command to the pre-approved list from Milestone 3 so the next run doesn’t stall.
    • The PR never opened. Almost always gh auth or a missing remote. Ask Claude to verify gh auth status and the remote URL, and to re-run the PR step.

    Going further

    • Run it again with the same PRD, but a cheaper model under the hood. Set one of the agents (say, the Builder) to a smaller Claude model by adding model: haiku to its agent file. Claude Code subagents can each run on a different Claude model. (Non-Anthropic models need a different harness. See codelab #4.) Same PRD, same pipeline, different cost. Compare the two runs side by side and decide whether the cheaper one was good enough.
    • Try an agent team. Subagents report back to one orchestrator. Claude Code also has an experimental agent teams mode, where several full Claude Code instances share a task list and message each other directly. Ask Claude to explain the difference and, if you’re curious, rerun the pipeline as a team. Expect it to cost noticeably more: each teammate carries its own full context.
    • Add a sixth agent: a QA-tester. Slot it between Builder and PR-opener. Give it a single job — run the code, write a one-paragraph test report, and refuse to hand off if a smoke test fails. Notice how this changes the cost profile and the quality of what reaches the Reviewer.
    • Try a workflow that’s genuinely not PRD-able and watch it fail. Write a PRD for “a board memo recommending whether we should raise prices next quarter” (about a made-up company, not yours). Run the pipeline. Read what comes back. The point isn’t to ship the memo — it’s to feel where this mode of work breaks, so you know the boundary by experience and not by lecture.

    Evals as a workflow

    Time
    60–90 minutes
    Difficulty
    Capstone
    Prerequisites
    Claude Code installed, an OpenRouter or Anthropic API key, plus access to one non-Anthropic model (e.g., Kimi K3 on Fireworks or OpenRouter)
    You will need
    A workflow with a checkable right answer — the default is support-ticket triage

    Why this matters

    This is the capstone. Every codelab before this one taught you a dial — model choice, harnesses, routing, retrieval, agents — and at the end of each you wrote a paragraph of impressions. Impressions are fine for learning. They are not fine for choosing what actually gets deployed. The moment someone on your team says “use this model for that feature,” or a vendor tells you “our AI resolves 60% of tickets,” the right question is how do you know? — and “it felt better” or a slide with one number will not survive that conversation.

    The professional answer is an eval: a small, repeatable test that scores models (or prompts, or harnesses, or retrieval setups) on a real task using a written rubric. Once you have one, the conversation changes. Instead of “I like Opus for this,” you say “on a ten-ticket triage rubric, Opus scored 4.3, Sonnet scored 4.1, Kimi scored 3.4 — and here’s where each one lost points.” That sentence is the difference between vibing and shipping. Today you’re going to build one, end to end, in an hour.

    What you’ll do

    • Pick a bounded workflow with a definable right answer (default: triaging a customer support ticket into category, priority, product area, escalation, and a one-line summary) and draft a scoring rubric with Claude.
    • Build a small test set — 5–10 synthetic inputs paired with reference answers you wrote by hand and trust.
    • Have Claude write the eval harness: run the model under test, send its output to a judge model, score against the rubric, dump the results to a CSV.
    • Run the same suite across three different models (e.g., a top-tier Claude model, a cheaper Claude model, and an open-weight model like Kimi) and rank them.
    • Inspect the spread, look at where models disagreed with the judge, and write a one-paragraph point of view on which model you’d actually deploy for this workflow.

    What you’ll actually learn

    The exercise is the surface. The real takeaways:

    • Without evals you’re vibing; with evals you’re shipping. Evals are how grown-ups make decisions about models, prompts, and workflows. They are the cheapest, highest-leverage thing you can do before deploying any AI workflow at scale.
    • The rubric is the hard part; the harness is plumbing. You will spend most of your time wording what “good” means. Once that’s pinned down, Claude can write the test runner in fifteen minutes.
    • Judge models work surprisingly well. Using an LLM to score another LLM’s output sounds like fox-guarding-henhouse logic, but for structured rubrics it is shockingly close to human grading — and it scales to thousands of runs.

    Milestone 1 · Pick the workflow and draft the rubric

    ~20 min

    Goal

    You have a written rubric — 4 to 6 criteria, each scored 1 to 5 with explicit anchors at 1, 3, and 5 — saved as rubric.md in your folder. The rubric describes what “good” looks like for the workflow you picked.

    Pick from this list

    The default is support-ticket triage because the output is bounded and most fields have an obvious right answer. If you’d rather pick a different bounded workflow, here are three alternatives that work just as well:

    • Support-ticket triage — default. Given a synthetic ticket, output a category (from a fixed list of about six), a priority (P1–P4, against written criteria), the product area, whether it needs escalation (security, billing dispute, outage), and a one-line summary. Easy to grade because most fields are right or wrong against your reference.
    • Contract key-term extraction from synthetic customer contracts — renewal date, term length, auto-renew yes/no, notice period, ARR. Structured output, gradable field by field.
    • Sales- or customer-call summary against a fixed structure (customer context / pain points / objections / next steps) from a synthetic transcript — gradable on faithfulness to the source and adherence to structure.
    • Quote extraction from a public earnings-call transcript (a public competitor’s works well) — every verbatim statement about pricing, AI, or headcount, with speaker. Gradable on accuracy and completeness.

    Nudges

    • Spend real time on the rubric. This is the part most people skip and it’s the part that matters most. If your rubric is mush, your scores will be mush.
    • Each criterion needs an explicit anchor at 1, 3, and 5. “Priority: 5” is useless. “Priority: 5 = matches the reference and the written P1–P4 criteria; 3 = one level off with a defensible reason; 1 = two or more levels off, or a P1 called a P3” is a rubric.
    • Decide which mistakes are expensive. Missing a buried security issue is far worse than tagging the wrong product area. Your rubric should say so, either with a heavier weight or a hard rule (“any missed escalation caps the overall score at 2”).
    • Ask Claude to push back on your rubric. Vague criteria are the silent killer. A good prompt is “critique my rubric like a grumpy head of support — where would two reasonable people disagree on the same output?”
    • Aim for 4–6 criteria. More than that and the judge gets noisy; fewer and you can’t tell models apart.

    Suggested prompts

    Paste into Claude

    I’m going to evaluate models on this task: given a customer support ticket for a made-up B2B SaaS product, output a JSON triage record with category, priority, product area, needs_escalation (plus the reason: security, billing dispute, or outage), and a one-line summary. First, help me write the triage spec the model will be given: a fixed list of about six categories (for example Bug, Billing, Account & access, How-to question, Feature request, Outage/performance), written criteria for each priority level P1–P4, the product areas, and exactly what counts as an escalation. Save it as triage-spec.md. Then draft a rubric with 4 to 6 criteria, each scored 1–5, with explicit anchors at 1, 3, and 5 for each criterion. Think about what a head of support would actually care about — right category, right priority against the written criteria, never missing an escalation (a missed security issue should hurt far more than a wrong product area), a summary that’s faithful to the ticket, valid output format. Save the result to rubric.md.

    Paste into Claude

    Now play grumpy head of support. Read the rubric back to me and tell me where two reasonable graders could disagree on the same model output. Tighten anything that’s vague, in the rubric and in the priority criteria in triage-spec.md.

    Why this works

    Writing the rubric forces you to articulate what you actually want, which is something most people only do after they’re unhappy with a model’s output. Do it first and the rest of the exercise becomes mechanical. This is the same skill that makes a good performance review, a good RFP, and a good prompt — you’re defining “good” in advance.

    ✓ You have rubric.md with 4–6 criteria. Each criterion has anchor descriptions at 1, 3, and 5. You can read the rubric to a colleague and they’d grade the same output the same way.

    Milestone 2 · Build the test set

    ~15 min

    Goal

    A folder of 5–10 paired files: each input (a synthetic support ticket) sits next to a reference answer you wrote by hand (the triage you’d stand behind if your head of support challenged it). These reference answers are your ground truth.

    Nudges

    • You don’t need real tickets, and you shouldn’t use them. Five to ten synthetic-but-plausible tickets will give you a meaningful signal. Ask Claude to generate them, then read each one to make sure it sounds like a real customer.
    • The reference answers are the part you must own. Write the ground truth by hand. Don’t let Claude write it and then grade against it — that’s circular. Generate the tickets with Claude, then triage each one yourself against triage-spec.md. If you can’t decide whether a ticket is P2 or P3, that’s not a chore to delegate; it’s a gap in your priority criteria. Fix the spec.
    • Mix easy and hard cases on purpose. A clear-cut bug report. A ticket that raises two unrelated issues. An angry customer whose rant buries a security concern. A feature request written up as a bug. An ambiguous billing question that might be a dispute or might be a how-to. Models look identical on easy cases; the spread shows up on the messy ones.
    • Keep the format consistent. Inputs all look the same; reference outputs all look the same. The judge will get confused if the structure wanders.

    Suggested prompts

    Paste into Claude

    Generate 5 synthetic support tickets for the made-up product in triage-spec.md, formatted like a Zendesk ticket (subject, customer plan tier, message body), with invented company and person names. Vary the difficulty: one clear-cut bug report; one ticket that raises two unrelated issues; one angry customer whose rant buries a possible security problem (for example, seeing another customer’s data); one feature request written up as a bug; one ambiguous billing question that could be a dispute or a simple how-to. Save them as inputs/case-01.md through case-05.md. Then walk me through each one briefly so I can check it reads like a real ticket — but don’t tell me how you’d triage it. I’ll write the answers myself.

    Paste into Claude

    For each input file, create a references/case-NN.json file with the triage fields (category, priority, product_area, needs_escalation, escalation_reason, summary) present but left blank, so I can fill them in by hand using triage-spec.md. I want to own the ground truth, not delegate it.

    Heads up

    The temptation to skip writing reference outputs is enormous — it’s the part of the work that feels least like “AI.” Don’t skip it. An eval with weak ground truth is worse than no eval, because it gives you a falsely confident answer. Fifteen minutes of triaging tickets yourself now saves you from a wrong recommendation later — and shows you how hard your support team’s everyday judgment calls really are.

    ✓ You have an inputs/ folder and a references/ folder, each containing 5 paired files. You’ve looked at each reference output and you stand behind it.

    Milestone 3 · Have Claude write the eval harness

    ~15 min

    Goal

    A small script that, given a model name and a folder of inputs, generates outputs from that model, sends each output plus the matching reference and rubric to a judge model, and writes the scores to a CSV.

    Nudges

    • This is the plumbing. Be clear with Claude about the data flow: input file → model under test produces a candidate output → judge model reads (rubric + reference + candidate) → judge returns scores in JSON → one row in the CSV. Drawing that flow on a sticky note before you ask is worth two prompts of clarification later.
    • Use OpenRouter (or whatever you set up in codelab #2) so swapping models is just changing a string. Don’t hardwire one provider.
    • Make the judge return structured JSON, not prose — one score per criterion plus a one-sentence justification. That’s what makes the CSV usable and the disagreements diagnosable.
    • Fields with one right answer (category, priority, escalation) can also be checked by plain code with an exact match against your reference. Do both. When the judge and the exact match disagree, one of them is wrong, and finding out which teaches you a lot.
    • Pick a strong, neutral judge model. The strongest model available when you run this is a sensible default (ask Claude to check OpenRouter’s current catalog). Ask Claude what the trade-offs are if you’re curious — this is a real research topic and it’s fine to learn the shape of it.

    Suggested prompts

    Paste into Claude

    Write a small Python script eval.py that takes a model name as a command-line argument, loops over every ticket in inputs/, sends each one through that model along with triage-spec.md to produce a JSON triage record, then sends the rubric, the reference answer, and the candidate output to a judge model (use the strongest Anthropic model on OpenRouter as the judge — check the current catalog), and gets back a JSON object with a score 1–5 for each rubric criterion plus a one-sentence justification per criterion. Also do a plain exact-match check of category, priority, and needs_escalation against the reference, recorded as extra criteria (exact_category, exact_priority, exact_escalation) scored 1 or 0. Append a row to results.csv for every input and criterion with columns: model_under_test, case_id, criterion, score, justification. Use OpenRouter for all model calls. Explain each piece in plain English as you write it.

    Paste into Claude

    Before we run it on all 5 cases and 3 models, run it on just one case with one model so I can see the raw judge JSON and make sure it’s sensible. Read the output back to me and tell me whether the scores look reasonable.

    Why this works

    Notice how short this milestone is. The rubric took twenty minutes; the harness takes fifteen. That ratio is the point. Once you can articulate “good,” the test runner is just plumbing — and plumbing is exactly the kind of work that Claude eats for breakfast.

    ✓ You can run python eval.py --model anthropic/claude-opus-5.5 against one input and see a sensible row appear in results.csv.

    Milestone 4 · Run across three models

    ~15 min

    Goal

    A populated results.csv covering all of your inputs across three different models, plus a small summary table showing average score per model per criterion.

    Nudges

    • Pick three models from different stables on purpose. A sensible trio: Anthropic’s current top-tier Opus model, its current Sonnet (cheaper and faster), and a strong open-weight model such as Kimi (hosted on Fireworks or OpenRouter). Model versions turn over every few months; ask Claude to check the current catalog and pick the equivalents. Either way, your comparison spans cost tier and provider.
    • Don’t hand-run three times. Ask Claude to write a small driver script that loops over the three model names so you have a single command that produces the whole results file.
    • Watch the cost as you go. Ask Claude to print a running tally. Evals can quietly burn through credits if you 10x your test set without noticing.
    • One of the runs will probably fail partway — rate limits, a malformed JSON response from the judge, an API hiccup. Don’t panic, paste the error into Claude, and let it add retry logic. That’s the loop.

    Suggested prompts

    Paste into Claude

    Write a tiny driver that runs eval.py across these three models: anthropic/claude-opus-5.5, anthropic/claude-sonnet-5.5, and moonshotai/kimi-k3. Check OpenRouter’s current catalog first and tell me if any of these have been superseded. Append all results to the same results.csv. Print a running cost estimate as it goes, and at the end print the cost per triaged ticket for each model (excluding the judge), plus what that implies per 10,000 tickets.

    Paste into Claude

    Now produce a summary table: average judge score per model per rubric criterion, plus an overall average per model. Show the exact-match checks separately as percent correct, and keep them out of the 1–5 overall average. Format it as a clean markdown table. Don’t round so aggressively that you hide the differences — one decimal place is fine.

    ✓ You have a markdown summary table with three rows (one per model), one column per rubric criterion, plus an overall average column. The three rows are not identical.

    Milestone 5 · Inspect the spread and write the POV

    ~15 min

    Goal

    One paragraph — the kind you’d send to your CTO or head of support over Slack — on which model you’d deploy for this workflow, why, what it costs per ticket, and where you saw it lose points.

    Nudges

    • The aggregate scores are the headline; the disagreements are the story. Look at any case where one model scored much lower than the others and read the judge’s justification. That’s where you learn what the model is actually bad at.
    • Also look at cases where all three models scored low. That’s probably a rubric problem or an input problem — not a model problem. A useful sanity-check.
    • Spot-check the judge. Pick two or three rows at random and grade them yourself against the rubric. If the judge consistently agrees with you, you can trust it. If it doesn’t, your rubric needs another pass.
    • The POV is not just “use Opus.” It’s “Sonnet matches Opus on category and priority at a fraction of the cost per ticket, but it missed the buried security issue that Opus caught — so I’d route routine tickets to Sonnet and send anything touching login, data access, or another customer’s information to Opus or a human.” That sentence is the deliverable.

    Suggested prompts

    Paste into Claude

    Look through results.csv and tell me: (1) which model wins overall, (2) which model wins on each individual criterion, (3) the three biggest disagreements between models — i.e., cases where one model scored very differently from the others — and what the judge said about each.

    Paste into Claude

    Now help me audit the judge. Pick three rows at random, show me the input, the candidate output, the reference, and the judge’s scoring. I’ll grade them myself and we’ll see how well the judge matched me.

    Paste into Claude

    Draft a one-paragraph point of view I could send to my CTO: which model would I use for ticket triage and why. Cite specific numbers from the eval, including the cost per ticket, and call out any missed escalations by name. Don’t be wishy-washy — make a call.

    Try this

    After you have your POV, change one word in your rubric — tighten or loosen a single anchor — and re-run the eval. Watch the ranking shift (or not). That’s the lesson: the rubric is a knob, and small changes to what you call “good” can flip which model looks best. The numbers are precise; precision is not the same as truth.

    ✓ You have a one-paragraph POV that names a winner, cites a specific number, names a concrete failure mode, and makes a recommendation. You could paste it into Slack right now.

    What you actually learned

    Surface lesson. You built a working eval suite from nothing in under ninety minutes. You wrote a rubric, assembled a small test set, had Claude build the harness, ran three models against it, and wrote a defensible recommendation grounded in numbers instead of vibes. That deliverable — rubric, scored CSV, one-paragraph POV — is exactly the artifact you should expect on your desk whenever someone asks “which model should we use for X?”

    Hidden curriculum. This codelab is the capstone for a reason. Every dial you played with earlier in the series — model choice in codelabs 1 and 3, routing in codelab 4, retrieval in codelab 7, agents in codelabs 9 and 10 — is a knob you can turn. Until today, you turned them by feel. Now you have a way to turn them with evidence. The rubric is the hard part; the harness is plumbing; the judge model is surprisingly good; and the whole exercise is the cheapest, highest-leverage thing you can do before deploying any AI workflow. Without evals you’re vibing. With evals you’re shipping.

    Where this shows up in your company. Any AI feature you ship to customers should come with an eval, and so should any vendor claim. When a vendor says “our AI resolves 60% of tickets,” ask to see the eval behind the number: what was the test set, who wrote the reference answers, what counts as “resolved,” and what happens on the other 40%. Better, run their tool and two alternatives through a rubric like yours on synthetic or heavily anonymized tickets. Inside your own teams, set the bar plainly: no AI workflow goes past one user, and no AI feature ships to customers, without an eval that someone can rerun. That same eval is what lets you swap to a cheaper or newer model when prices drop — which is how you keep model lock-in and inference cost per customer under control rather than taking them on faith. And notice where your time went today: the rubric. Deciding that a missed security escalation is worse than a wrong category, or what separates P2 from P3, is a product and leadership call, not an engineering detail. Don’t leave it to whoever happens to write the harness. The next time you need to pick a model for a workflow you care about — contract extraction, call summaries, release notes — you have a template. Copy this folder, swap the rubric, swap the inputs, run it. That’s the workflow.

    If you got stuck

    The single most useful prompt in this entire codelab — keep it in your back pocket:

    Paste into Claude

    Here’s exactly what I saw on my screen: [paste]. Explain to me in plain English what’s going on, then tell me what to try next. If you can fix it yourself, do that.

    Common stuck points:

    • My rubric feels mushy and I can’t tighten it. Ask Claude: “Give me three different model outputs for the same input — one clearly great, one mediocre, one bad. Score each one against my rubric and show your reasoning, so I can see where my anchors break down.”
    • The judge keeps returning prose instead of JSON. Ask Claude to add a structured-output constraint or a schema to the judge prompt, and to retry once with stricter instructions if parsing fails.
    • All three models scored almost identically and I can’t tell them apart. Either your inputs are too easy or your rubric is too coarse. Ask Claude: “Suggest three harder inputs that would force the models to differentiate, and tighten my rubric’s top anchors.”
    • One model wins on every criterion and it’s suspicious. Check that you’re not using the same model family as both the model-under-test and the judge. Ask Claude: “Could there be a self-preference bias here? Suggest a neutral judge and re-run.”
    • The eval cost is climbing faster than I expected. Ask Claude to print a per-model cost estimate before each run starts, and to cache judge results so you don’t re-score outputs you’ve already graded.

    Going further

    • Wire your eval to run nightly on a small cron job, so you have a continuous read on whether the model you deployed is still the best one as new releases drop. Ask Claude to set it up — it’s another exercise in handing the agent a CLI.
    • Add a second workflow to your eval suite (contract key-term extraction or a call summary from the list in Milestone 1). Now you have a small set of evals that map workflows to model recommendations — the seed of a company-wide “which model for which job” matrix.
    • Turn it on a vendor. Take an AI support tool you’re evaluating (or already pay for), run your synthetic tickets through it, and score it on the same rubric as the raw models. Now you know what the vendor adds over a model plus a good prompt, and whether it’s worth the price.
    • Run the same eval against the same model with three different prompts. Now you’re evaluating prompts instead of models — same harness, different dial. This is how serious AI teams iterate.
